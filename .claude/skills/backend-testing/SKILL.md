# Backend testing

`packages/api` has three jest modes and a container-level suite. Most of the difficulty
here is not writing assertions — it is that several failure modes present as a broken
API rather than as a test-harness detail.

## Where a test belongs

| Mode | Location | Use for |
|---|---|---|
| `test:unit` | `src/**/__tests__/*.unit.spec.ts` | Pure logic. No database, no container. Fast — prefer this. |
| `test:integration:modules` | `src/modules/*/__tests__/**` | A module's own service behaviour. |
| `test:integration:http` | `integration-tests/http/*.spec.ts` | A real booted app: routes, workflows, subscribers, events. |
| `deploy/smoke-test.sh` | `deploy/` | Anything only reachable at container level — boot guards, the production config overlay, shell scripts. Runs on pull requests only. |

Boot guards now live in `packages/api/src/lib/production-overlay.ts`, which **is** inside
jest's `src/**` reach, so they are unit-testable — see
`src/lib/__tests__/production-overlay.unit.spec.ts`. The smoke suite still covers what
unit tests cannot: that the *compiled artifact* loads inside a real container.

## Four traps

**1. The runner reads `DB_HOST`, not `DATABASE_URL`.** It creates a per-run database from
`DB_HOST` / `DB_PORT` / `DB_USERNAME` / `DB_PASSWORD`. Set only `DATABASE_URL` and it
silently tries `localhost:5432` and dies with a bare `AggregateError`. Both are needed and
both are in the committed `packages/api/.env.test`.

**2. The database is restored between `it` blocks.** `beforeAll` fixtures survive via a
snapshot; rows created *inside* a test do not. Split a flow across several `it` blocks and
the second 404s on what the first just created.

> Keep a flow that builds on itself in **one `it`**, however long. Say so in a comment —
> it looks like a mistake otherwise. See `multi-seller-checkout.spec.ts`.

**3. Integration tests cannot run from a nested git worktree.** Under
`.claude/worktrees/*`, Node resolution reaches both the worktree's and the parent
checkout's `node_modules`. Nested workflow steps then cross two copies of `awilix` and
fail with:

```
parentContainer[ROLL_UP_REGISTRATIONS] is not a function
```

It surfaces as a **500 on a route** — `POST /store/carts/:id/shipping-methods` hits it —
so it reads like a broken endpoint. Simpler specs never invoke a nested workflow, so the
suite looks healthy. Run from a flat clone, as CI does:

```bash
git clone --quiet . /tmp/flat && cd /tmp/flat
npm install --force && npm run codegen
cd packages/api && npm run test:integration:http
```

**4. A notification row exists before it is sent.** `createNotifications` persists the row
and hands it to a provider afterwards, so polling until a row exists and then asserting
`status === "success"` is a race that a slower runner loses. Wait for a *settled* row:

```ts
const settled = <T extends { status?: string }>(rows: T[]): T[] | null =>
  rows.length && rows.every((r) => r.status !== "pending") ? rows : null
```

## Running

Postgres and Redis must be up; settings are in `packages/api/.env.test`.

```bash
docker run -d --name mercur-test-pg -p 5433:5432 \
  -e POSTGRES_USER=medusa -e POSTGRES_PASSWORD=medusa -e POSTGRES_DB=medusa-test postgres:16-alpine
docker run -d --name mercur-test-redis -p 6380:6379 redis:7-alpine
```

These are usually started with `--rm`, so stopping them **deletes** them; `docker start`
then no-ops and the suite fails at boot with a null container. Recreate with `run`.

The full set, which is what CI runs:

```bash
npm run codegen && npm run check-types && npm run lint
npm run test:unit --workspace @acme/api
npm run test:integration:http --workspace @acme/api
```

## `check-types` passes locally and fails in CI

`container.resolve("<module>")` is only typed when `.medusa/types/modules-bindings.d.ts`
exists — generated by a Medusa build and gitignored, so present locally and absent on a
fresh runner. Inferring a module service's type from `resolve` typechecks here and fails
there with `TS2571: Object is of type 'unknown'`.

Declare the slice you use and cast at the boundary. To check the way CI sees it:

```bash
mv packages/api/.medusa/types /tmp/types-bak
(cd packages/api && npx tsc --noEmit)
mv /tmp/types-bak packages/api/.medusa/types
```

## Standards

- **A test nobody has seen fail is not evidence.** After writing one, break the thing it
  covers and confirm it goes red. Say in the commit what you broke.
- **Assert the thing that fails soft.** A lookup that degrades gracefully — a store name,
  a seller name — leaves every test green when it breaks. Persist it and assert it.
- **Explain the constraint in the test.** Anything that looks like a mistake but is not
  (one long `it`, an unusual wait) needs a comment, or someone will "fix" it.
